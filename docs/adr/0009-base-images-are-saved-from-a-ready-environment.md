# Base images are saved from a Ready Environment

`devcrate save-image` makes a repo's Base image by snapshotting a Ready Environment's root disk, after setup has run on it, instead of building one on a separate builder VM that clones the repo and runs the setup scripts. We chose this because the Environment already holds the clone, the credentials and the result of setup, so the image matches what setup produced, with no second clone and no builder lifecycle in any Provider. Before the snapshot, devcrate removes its own state from the root disk (the Agent, cloud-init's per-instance state, the volume's `/etc/fstab` line) and disables Docker so a booted image cannot start it before the volume is mounted, then shuts the VM down, snapshots it and destroys the instance, keeping the volume, the same end state as a Stop: a scrubbed VM has no idle stop, and a powered-off disk snapshots consistently. A Base image is labelled with the repo's base Environment name, which `up` records on the volume, and is shared by its worktree Environments. A save deletes every older one only once it is complete, and `up` uses the newest, so an interrupted save or two worktrees saving at once settle on one image without a lock. The Provider finds it by that label in `up` (ADR 0002), it takes precedence over the `image` option, and `delete` leaves it, since it belongs to the repo and not to one Environment: the same `save-image` verb deletes it with a `delete` request flag, and `status` returns it so its storage bill is visible. Anything setup writes under `/var/lib/devcrate` lands on the volume, not in the image, which is correct because the volume comes back on every `up`. Changing to builder VMs later would change the `save-image` verb in every Provider.
