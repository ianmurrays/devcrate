# Repos are trusted with their VM

A repo you `up` is trusted with root on its Environment's VM, so devcrate does not sandbox it from anything on the VM: the `devcontainer up` process keeps the full setup environment (every `forward_env` value, the forwarded SSH agent), and a repo's `build.options` may name any env var or any root-readable file (including the Self-stop token) as a BuildKit secret. We chose this over scrubbing the environment down to an allowed list because the repo already runs code as root on the VM through `initializeCommand` and its `setup_script`, so an allowlist would protect nothing while costing configuration. The boundary devcrate does hold is on the laptop: which secrets leave it is set only in the user config (`forward_env`, `forward_env_commands`, `forward_files`, `forward_agent`), never in `.devcrate.toml`. Running an untrusted repo safely would need a different design (no secrets forwarded, no Self-stop token on the VM), not a tighter allowlist.
